## Confirmed review findings

### P1 Failed response usage can disappear

At [router.py](../kernel/biz_kernel/models/router.py#L159), usage is collected only
after `port.structured` returns. If the adapter reports usage and then raises, the
exception path omits that attempt's usage; the first failed attempt has no attached
result at all. A mocked actual Claude adapter with no tool-use block reported
`$0.000045`, while `spent_before` returned `None`. No provider was contacted.

This can understate incurred cost and budget spend and makes comparison evidence
incomplete. Fix first and later failed attempts, preserve retryable exception types,
and distinguish unreported usage from a reported zero. Each paid attempt must be
accounted once, including failures.

### P1 Generic escalations are absent from task activity

[runner.py](../kernel/biz_kernel/workflows/runner.py#L731) publishes the generic
confidence/signal escalation packet and audit record without linked task evidence
or an alert. The owner task API reads evidence events. A disposable PostgreSQL
reproduction produced **one escalation packet, zero task activity entries and zero
alerts**. The open task therefore lacks the reason the owner must act.

Link the escalation and actionable reason to the task idempotently. Test low
confidence in both compositions, replay exactly once and zero external writes.
This is separate from the explicit service-request escalation added in PR 16.

### P2 Evaluation and runtime disagree on schema dialects

[harness.py](../kernel/biz_kernel/models/eval/harness.py#L225) checks every case as
Draft 2020-12. The router and training capture accept a schema's declared dialect.
A valid Draft4 schema using boolean `exclusiveMinimum` passes runtime validation
but is refused by the evaluation loader. Align validation with the declared dialect
and retain the existing private-data and reference restrictions.

### Integration must preserve the stricter model boundary

A virtual merge of `7c772ba` into PR 16 conflicts in five files: `deploy/browser_demo.py`,
`deploy/preflight.py`, `kernel/biz_kernel/tools/shadow.py`, the task detail page and
the owner-console browser test. The alternate branch has useful canonical UUID and
recorded shadow-verdict presentation work.

Its model guard also treats arbitrary private-network IPs as local. A pure-function
probe accepted `http://10.20.30.40:11434` in shadow mode without opt-in; PR 16 refused
it. Retain PR 15's strict appliance boundary and selectively port the console work.
The probe sent no requests. Validate canonical UUID task links, shared-job scoping
and labels/verdicts from recorded evidence after reconciliation.

## Comparison contract

- Comparisons are for learning on **tuning data**. Keep held-out cases out of tuning
  and ordinary per-case inspection. Do not relabel private cases as public or forge
  historical receipts to make the new executor work.
- A structurally complete candidate is insufficient authorization. The exact version
  and cohort must have the required immutable owner testing review/attestation.
  A successor cannot repair missing historical evidence by declaring new hashes;
  genuine captured provenance is still required.
- Historical observed output, often lacking a model revision, is reference evidence.
  It is not a freshly measured baseline. Evaluate both prompts with the same model,
  settings, case/check set and timeout contract.
- Use a host-side local comparison executor for this sprint, using literal loopback
  Ollama and a verified installed digest. The console enqueues/polls a durable job.
  Compose execution is deferred; any future gateway support must explicitly pin
  the appliance rather than admit arbitrary private-network hosts.
- Checkpoint each side/case through DBOS and bind job idempotency to version, cohort,
  prompts, scorer and model hashes, backend version, generation settings, timeout,
  seed and repetition count. Duplicate requests reuse work; crashes preserve
  provisional or unknown attempts, latency, usage and incurred cost. Report local API cost
  separately from hardware/electricity, which are not measured here.
- A baseline-pass to candidate-fail transition is a regression even when the aggregate
  score improves. Missing results, inference errors, altered evidence or model drift
  invalidate the comparison. Record the target case and all conflicting older cases.
- A comparison changes no deployed prompt/SOP, policy, permission or autonomy. It
  cannot claim held-out readiness, production safety or time saved. Activation and
  rollback require their own later versioned release workflow and business gates.

## Upgrade proof and owner work

The packaged upgrade drill should start with the actual older release and a
populated `0023` database containing pending work. Demonstrate refusal without
schema mutation, drain that work on the original build, then upgrade through `0024`
and the new version/cohort/comparison migrations to the final shipping head.
Restart and replay while preserving corrections, audit history and exactly-once
effects. Existing unit refusal tests and same-build restore tests are useful but
do not replace that transition proof.

Owner work remains parallel to coding: supply and confirm HIVE history, time 20 real
tasks, count normal-week volume, provide actual business material and configure the
Mac mini/model/M365 tenant and authentication-header sample. Stage 1 still needs the
held-out model gate and two weeks of shadow operation. Stage 2 still requires its
learning and sustained time-saving evidence. M7–M9 remain frozen.

Cut line: defer visual polish and extra shadow-verdict presentation if integration
uses the reserve. Keep cost correctness, private provenance, version-specific review,
per-case regression reporting and durable execution in the committed scope. Production
outcome capture, operator notification delivery, public signing and rule activation
remain later work.
